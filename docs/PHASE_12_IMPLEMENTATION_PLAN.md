# Phase 12 – Implementierungsplan: Freitext-KI-Angebotsfeature (Teil A)

Stand: 2026-08-23. Basiert auf `PHASE_12_AP0_DISCOVERY.md` (AP0) und ChatGPTs fünf verbindlichen Architekturentscheidungen dazu (2026-08-23, "GO für AP1 = Implementation Plan"). Analog Phase 6–11: dieser Plan geht vor jedem AP1-Code an ChatGPT zur Prüfung, danach an den Nutzer für das explizite Implementierungs-GO.

## 1. Verbindliche Architekturentscheidungen (ChatGPT, 2026-08-23)

1. **Kein dauerhafter Freitext-Speicher.** Freitext wird nur für die Extraktion verarbeitet, nie in `AuditLog`, `AnalyticsEvent` oder einem dauerhaften Customer-Datensatz persistiert — höchstens transaktionsnah/in-memory im Request-Handler. Die KI-Rohantwort wird ebenfalls nicht dauerhaft gespeichert. Nur bestätigte Werte landen als normale `CustomerAnswer`.
2. **Einzelbestätigung als Standard, keine Sammel-Übernahme.** Jeder Vorschlag hat eigene Aktionen (übernehmen/ändern/verwerfen); eine globale "Alle übernehmen"-Funktion ist in Phase 12 nicht erlaubt.
3. **Kein Alt-Neu-Vorschlag bei bereits beantworteten Fragen.** Nur unbeantwortete sichtbare Fragen sind KI-Kandidaten; eine bestehende aktive `CustomerAnswer` wird von der KI weder verändert noch durch einen Vorschlag ersetzt.
4. **`SHORT_TEXT` als KI-Ziel ausgeschlossen.** Erlaubte Zielantworttypen: `SINGLE_CHOICE`, `MULTIPLE_CHOICE`, `BOOLEAN`, `INTEGER`, `DECIMAL`, `DATE`.
5. **Mehrdeutigkeit wird konsequent verworfen**, nie geraten. Die KI darf keine neuen `Question`-Keys, Antwortoptionen oder Werte erfinden.

Zusätzliche harte Sicherheitsgrenze (ChatGPT): **die KI darf niemals selbst bestimmen, welche Fragen sichtbar sind.** Der Server berechnet zuerst den aktuellen sichtbaren Fragenkatalog (über die bestehende `computeVisiblePath()`-Logik); nur dieser Katalog geht an die Extraktionskomponente. Niemals umgekehrt (Session → KI → KI entscheidet, welche Fragen existieren) — wichtig für Tenant-Isolation, Fragebogen-Versionierung und IDOR-Schutz.

**Scope-Grenze (bindend):** Phase 12 endet bei der bestätigten strukturierten Beratung. Erlaubt: Freitext → bestehende sichtbare Frage → strukturierter Kandidat → Mitarbeiter bestätigt → normale `CustomerAnswer`. Nicht erlaubt: Freitext → neue Frage; Freitext → erfundene Antwortoption; Freitext → automatische `CustomerAnswer`; Freitext → Überschreiben bestehender Antworten; Freitext → `SHORT_TEXT`-`CustomerAnswer`; Freitext → dauerhafte Rohtextablage; KI → Recommendation Engine direkt. Automatischer Vertragsabschluss/Provider-API/Bestellung/Aktivierung (Teil B) bleibt vollständig separat.

## 2. Architektur: zehn Schichten (ChatGPT-Vorgabe) auf konkrete Module abgebildet

| --- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Extraction Contract                 | `src/server/ai-extraction/contract.ts` — providerunabhängiges TS-Interface (`AiExtractionProvider.extract(input): Promise<ExtractionCandidate[]>`), kein Provider-spezifischer Typ leckt nach außen                                                                                                                                                                                                                                                          |
| 2   | Visible-Question Context            | Wiederverwendung der bestehenden `computeVisiblePath()`-Logik (Fragen-Engine, Phase 3A) — liefert genau den Fragenkatalog (`key`/`label`/`answerType`/`AnswerOption[]`/`minValue`/`maxValue`), der an Schicht 3 übergeben wird. Kein neuer Sichtbarkeits-Code.                                                                                                                                                                                               |
| 3   | AI Extraction                       | `src/server/ai-extraction/providers/` — zunächst NUR ein deterministischer `MockExtractionProvider` (synthetische Testdaten, siehe Abschnitt 5); echte Provider-Anbindung ist ein separater, später zu genehmigender Schritt (Abschnitt 4, AP5)                                                                                                                                                                                                              |
| 4   | Server Validation                   | `src/server/ai-extraction/extraction-validator.ts` — analog `goal-validator.ts`/`commission-validator.ts`: prüft jeden Kandidaten gegen den tatsächlichen sichtbaren Fragenkatalog (`questionKey` bekannt+sichtbar), `answerType`-Konsistenz, `AnswerOption`-Gültigkeit, `minValue`/`maxValue`/`minLength`/`maxLength`/`minSelections`/`maxSelections`, `SHORT_TEXT` wird hart ausgefiltert. Ungültige/unsichere Kandidaten werden verworfen, nicht anzeigt. |
| 5   | Suggestion State                    | **Kein neues Datenmodell.** Vorschläge existieren ausschließlich als Response-Payload der Extraction-API + client-seitiger React-State in der Frage-Flow-UI, bis der Mitarbeiter bestätigt/verwirft. Keine Persistierung vor Bestätigung.                                                                                                                                                                                                                    |
| 6   | Employee Confirmation               | Unverändert der bestehende `CustomerAnswer`-Speicherpfad (Service-Schicht Phase 3A/3B) — ein bestätigter Vorschlag durchläuft exakt denselben Validierungs-/Speicherweg wie eine manuell eingegebene Antwort, keine Sonderbehandlung.                                                                                                                                                                                                                        |
| 7   | Audit                               | Siehe Abschnitt 3 (offene Frage: `AnalyticsEvent` vs. `AuditLog` — zur Entscheidung an ChatGPT). Nur technische Metadaten (Session-ID, Anzahl Vorschläge, Modell-/Prompt-Version als String/Enum, je Feld `questionKey`+`accepted`/`changed`), niemals Freitext oder KI-Rohantwort.                                                                                                                                                                          |
| 8   | Privacy/Retention/Provider Boundary | Freitext verlässt den Request-Handler ausschließlich über den `AiExtractionProvider`-Contract (Schicht 1); kein anderer Code-Pfad erhält Zugriff auf den Rohtext. Kein Logging des Freitexts (auch nicht in Server-Logs/Error-Traces — explizit zu prüfen in AP-Sicherheitsreview).                                                                                                                                                                          |
| 9   | Failure/Timeout/Cost Controls       | Bei Provider-Fehler/Timeout: keine Vorschläge, normaler Fragen-Flow bleibt vollständig unbeeinflusst (Feature ist rein additiv, nie blockierend). Konkrete Timeout-/Kosten-/Retry-Werte erst mit der echten Provider-Anbindung (AP5) endgültig festgelegt.                                                                                                                                                                                                   |
| 10  | Tests/Security/E2E                  | Siehe Abschnitt 5.                                                                                                                                                                                                                                                                                                                                                                                                                                           |

## 3. Offene Punkte für ChatGPT-Prüfung (bewusst nicht selbst entschieden)

1. **Audit-Modell:** `AuditLog` (Prisma-Modell `AuditLog`, `action: AuditAction` CRUD-artig, `entityType`/`entityId` Pflichtfelder — bisher nur für Admin-/Config-Mutationen wie Goal/RuleSet/CommissionModel verwendet) oder `AnalyticsEvent` (`AnalyticsEventType`-Enum, bereits das etablierte Muster für Konsultations-Flow-Ereignisse wie `QUESTION_ANSWERED`/`ANSWER_CHANGED`)? Fachlich passt `AnalyticsEvent` besser (Konsultations-Zeitpunktereignis, kein Entity-Mutations-Audit), würde eine Erweiterung von `AnalyticsEventType` um z. B. `AI_EXTRACTION_REQUESTED`/`AI_SUGGESTION_ACCEPTED`/`AI_SUGGESTION_REJECTED` bedeuten. Bitte Entscheidung vor AP1.
2. **Feature-Aktivierung/Gating:** Soll das Feature hinter einer neuen Berechtigung (analog `config.*`-Namespace, aber für ein Laufzeit-Feature statt einer Admin-Konfiguration) oder einem einfachen Tenant-Feature-Flag stehen, oder ist es für alle Mitarbeiter mit bestehendem Konsultationszugriff automatisch verfügbar? Relevant wegen Kosten (externe KI-Aufrufe) und weil manche Tenants das Feature evtl. aus Datenschutzgründen nicht wollen.
3. **API-Platzierung:** Neue Route unter `src/app/api/consultation/sessions/[id]/ai-extraction` (analog bestehendem Konsultations-Routing) — zur Bestätigung.
4. **Reihenfolge Mock- vs. echte Provider-Anbindung:** Vorschlag, AP1–AP4 vollständig mit `MockExtractionProvider` (deterministische synthetische Kandidaten) zu bauen und zu testen, die echte externe Provider-Anbindung (Modellwahl, Kosten, Prompting) als eigenes AP5 mit separatem, explizitem GO zu behandeln — passt zur bestehenden Projektregel "nur synthetische Testdaten" und trennt die reine Architekturarbeit von der Provider-/Kostenentscheidung. Bitte Bestätigung.

## 4. Arbeitspakete (Vorschlag)

- **AP0** – Discovery (bereits erledigt, `PHASE_12_AP0_DISCOVERY.md`).
- **AP1** – Extraction Contract (Schicht 1) + Visible-Question-Context-Adapter (Schicht 2, Wiederverwendung `computeVisiblePath()`) + `MockExtractionProvider` (Schicht 3, synthetisch/deterministisch) + `extraction-validator.ts` (Schicht 4). Reine Server-Bausteine, kein UI, keine API-Route, keine echte Provider-Anbindung.
- **AP2** – API-Route(n) für Extraktionsanfrage (Request → sichtbarer Fragenkatalog → Mock-Provider → Validator → Response mit validierten Kandidaten). Keine Persistierung (Schicht 5 bleibt client-seitig).
- **AP3** – Bestätigungs-UX in der Frage-Flow-UI (Schicht 5+6): Vorschlags-Markierung je Feld mit übernehmen/ändern/verwerfen, Einzelbestätigung, kein Bulk. Bestätigter Vorschlag läuft durch den unveränderten `CustomerAnswer`-Speicherpfad.
- **AP4** – Audit/Nachvollziehbarkeit (Schicht 7, gemäß ChatGPTs Entscheidung aus Abschnitt 3 Punkt 1) + PII-Scanner-Verifikation, dass Freitext/Rohantwort tatsächlich nirgends landen (Schicht 8).
- **AP5** – Echte externe Provider-Anbindung (Modellwahl, Prompting, Kosten-/Timeout-Konfiguration, Schicht 9) — eigener, separat zu genehmigender Schritt, NICHT Teil des initialen Implementierungs-GOs.
- **AP6** – Security/Regression/E2E (Desktop+Tablet, gleiche Härte wie Phase 8–11): Tenant-Isolation des Prompts, RBAC/Feature-Gating (falls aus Abschnitt 3 Punkt 2 beschlossen), Bestätigungs-/Verwerfungs-Flow, Regressionsschutz "bereits beantwortete Frage bleibt unverändert", `SHORT_TEXT`-Ausschluss, Mehrdeutigkeits-Verwerfung.
- **AP7** – Dokumentation (neues `docs/AI_EXTRACTION.md` analog `QUESTION_ENGINE.md`/`RECOMMENDATION_ENGINE.md`).
- **AP8** – Abschlussbericht Phase 12 (Teil A).

## 5. Tests (Grundsatz)

Tenant-Isolation-Negativtest; E2E: Bestätigungs-/Änderungs-/Verwerfungs-Flow, Regressionstest für bereits beantwortete Fragen). Tests für die echte Provider-Anbindung (AP5) folgen erst nach der separaten Genehmigung dieses Schritts.
